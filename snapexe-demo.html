OpenSearch Backup & Restore Demo

A full lifecycle walkthrough: inspect the source cluster, back it up to S3 with the snapexe-oss skill, restore into a fresh destination, then tear everything down - each step with a copy button. Credentials come from AWS Secrets Manager; AWS access uses the IAM-role credential chain.

Before you start

  • All four containers up: os-source-hot, os-source-warm (source, ports 9200/9202) and os-dest-hot, os-dest-warm (dest, 9201/9203).
  • AWS identity resolves via the credential chain - aws sts get-caller-identity returns account 765423874566, region us-west-2.
  • Secret snapexe/opensearch exists in us-west-2 (holds the opensearch_source / opensearch_dest creds).
  • Run all Terminal steps from the repo dir, in the same shell so the password variables persist. Paste Claude prompts into Claude Code.
  • This demo assumes the destination starts with only system indices (a fresh dest). Tag used throughout: demo.
0

Set up the shell

Pull each cluster’s user:password from AWS Secrets Manager into a variable - the same secret the skill uses, read via the IAM-role credential chain. (Run from the repo directory.)

Terminal · run once
# fetch admin user:password for each cluster from Secrets Manager
SCRED=$(aws secretsmanager get-secret-value --secret-id snapexe/opensearch --region us-west-2 --query SecretString --output text | python3 -c "import sys,json;c=json.load(sys.stdin)['opensearch_source'];print(c['username']+':'+c['password'])")
DCRED=$(aws secretsmanager get-secret-value --secret-id snapexe/opensearch --region us-west-2 --query SecretString --output text | python3 -c "import sys,json;c=json.load(sys.stdin)['opensearch_dest'];print(c['username']+':'+c['password'])")
Note: this reads the credentials from Secrets Manager, matching how the skill authenticates - no local creds file needed. If you get ResourceNotFoundException, your shell is on a different account/region: check aws sts get-caller-identity (want 765423874566) and keep --region us-west-2.

Show what’s in the source cluster

List the nodes (hot / warm), the indices, the data streams, and the searchable-snapshot indices on the source (9200).

Terminal · nodes (hot / warm)
curl -sku "$SCRED" "https://localhost:9200/_cat/nodes?v&h=name,node.roles,master"
Terminal · indices
curl -sku "$SCRED" "https://localhost:9200/_cat/indices?v&s=index"
Terminal · data streams
curl -sku "$SCRED" "https://localhost:9200/_data_stream?pretty"
Terminal · searchable snapshots
curl -sku "$SCRED" "https://localhost:9200/_all/_settings/index.store.type?flat_settings=true" | jq

ExpectTwo nodes - os-source-hot (cluster_manager,data,ingest) and os-source-warm (warm); data indices such as logs, orders, users; a logs-datastream data stream; and logs-searchable reported as remote_snapshot.

Confirm the destination is empty

Show the dest nodes (hot / warm) and confirm it contains only system indices before we restore into it.

Terminal · nodes (hot / warm)
curl -sku "$DCRED" "https://localhost:9201/_cat/nodes?v&h=name,node.roles,master"
Terminal · indices
curl -sku "$DCRED" "https://localhost:9201/_cat/indices?v&s=index"

ExpectTwo nodes - os-dest-hot (cluster_manager,data,ingest) and os-dest-warm (warm); and only system indices (.opendistro_security, .plugins-ml-config, plus any auto-regenerated security-auditlog-* / top_queries-*). No logs/orders/data streams.

3

Back up the source cluster

Prompt Claude Code - the snapexe-oss skill provisions the S3 bucket + IAM user, installs the keystore keys on both source nodes, and starts the snapshot.

Prompt Claude Code
Using the snapexe-oss skill: back up my source OpenSearch cluster at
https://localhost:9200 to S3 with tag "demo", using the Secrets Manager
secret snapexe/opensearch for credentials. It is a 2-node cluster (Docker
containers os-source-hot and os-source-warm) with no repository set up yet -
provision the bucket + IAM user and install the keystore keys on both nodes,
in us-west-2.

ExpectWith no indices named, the backup covers the whole cluster - all hot indices and data streams (searchable snapshots are recorded for remap). Claude confirms it will create real AWS resources, provisions snapexe-demo-* (bucket + IAM user), installs keys on both nodes, and reports “Snapshot started”.

Why both nodes? The repository is verified on every node, so the S3 keystore keys must be installed on os-source-hot and os-source-warm. The skill handles this; the single-node --auto-provision shortcut alone would fail verification on the warm node.

Check the snapshot status

Prompt Claude Code
Show me the status of the "demo" snapshot.
Terminal (equivalent)
.venv/bin/python opensearch_snapshot.py status --tag demo --secret-id snapexe/opensearch

ExpectState: SUCCESS with 100% of shards complete.

Restore into the destination cluster

Prompt Claude Code to restore the snapshot into the dest (9201), including the data stream and searchable snapshot.

Prompt Claude Code
Using the snapexe-oss skill: restore the "demo" snapshot into the destination
cluster at https://localhost:9201, including the data stream and the searchable
snapshot. It is a 2-node cluster (os-dest-hot, os-dest-warm); use the secret
snapexe/opensearch.

ExpectClaude registers the repo on the dest, restores the regular indices, restores logs-datastream via the superadmin cert, re-attaches logs-searchable, and reports “Restore started”.

6

Check the restore status

Restore is asynchronous - watch recovery, then confirm the data landed on the dest.

Terminal · active recovery
# empty table once recovery is done
curl -sku "$DCRED" "https://localhost:9201/_cat/recovery?v&active_only=true"
Terminal · restored indices
curl -sku "$DCRED" "https://localhost:9201/_cat/indices?v&s=index"
Terminal · restored data stream
curl -sku "$DCRED" "https://localhost:9201/_data_stream?pretty"

ExpectRecovery drains to empty; the dest now shows logs, orders, users, logs-searchable, and the logs-datastream data stream - matching the source.

7

Tear down the resources

Prompt Claude Code to delete everything tag demo created, then verify each resource is gone.

Prompt Claude Code
Using the snapexe-oss skill: delete all the AWS and repository resources for
tag "demo". Do a dry-run first, show me the preview, then delete.
Verify · S3 bucket gone
# expect no snapexe-demo line
aws s3 ls --region us-west-2 | grep snapexe-demo
Verify · IAM user gone
# expect a NoSuchEntity error
aws iam get-user --user-name snapexe-demo-user
Verify · config file gone
# expect "No such file"
ls -l snapexe-demo-config.json
Verify · repo deregistered
# expect {} (empty)
curl -sku "$SCRED" "https://localhost:9200/_snapshot/snapexe-demo*?pretty"

ExpectNo snapexe-demo bucket, NoSuchEntity for the IAM user, no config file, and {} for the repository - everything the tag created is gone.

Note: delete-all deregisters the repo on the source (the config’s endpoint) and removes the bucket/IAM/config. The restored data on the dest and the dest-side repo registration are left in place - remove those separately if you want a clean slate to re-run the demo.
